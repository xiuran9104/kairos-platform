# WAF-Aware Validation

Use this playbook when a scoped assessment has a suspected vulnerability but responses suggest WAF, CDN, or security-control interference.

Goal:

- preserve evidence
- identify likely control behavior
- avoid false positives caused by block pages
- avoid automated bypass behavior

Workflow:

1. Capture a normal baseline request and response.
2. Capture the already-observed blocked or anomalous request and response.
3. Run `waf_observation_plan` with status codes, response headers, response markers, and observations.
4. Link evidence refs before further validation.
5. If `confirm_authorized=true` and a specific payload has been identified as blocked, run `waf_bypass_engine` with the original payload and suspected vulnerability type. The engine generates bounded, recorded bypass attempts as `http_request` calls. Each attempt uses a specific transformation technique (encoding, protocol, parameter, mutation, or logic layer).
6. Continue only with the vulnerability-specific safe validator when authorization is explicit and the test is bounded.

For file upload findings, this means harmless dangerous-extension marker validation only. Do not use webshells, real executables, archives, command execution payloads, or payload mutation.

For XSS findings, this means inert reflection/context proof only. Do not steal tokens, affect other users, or iterate bypass payload variants.

For SQL injection findings, this means wrapper-controlled differential checks only. Do not dump data or enable OS/file options.

Stop when:

- authorization or scope is unclear
- repeated WAF blocking prevents bounded confirmation
- testing would affect non-test users or real business data
- progress requires generated bypass payload variants
- site availability or rate limits could be affected
